# 개요와 진행 현황

## 1. 배경과 목적

**러너는 청소년 대상 AI 위험평가 벤치마크에서 문항을 받은 뒤의 모델 실행, 판정 입출력, 지표 집계, 납품 변환을 맡는 코드다.**

- 과제는 ETRI의 청소년 대상 AI 위험평가 벤치마크 구축이며, 발주·수요 기관은 AISI임. 벤치마크는 청소년에게 위험할 수 있는 상황을 담은 위험 문항과 과잉거절을 보기 위한 대조 문항(`case_type=safe_control`)을 여러 AI 모델에 같은 조건으로 보내고, 응답을 채점해 지표로 비교하는 체계임
- 러너는 데이터 구축과 모델 평가를 맡은 연구실 A가 만듦. 연구실 A 결정이나 제안으로 적힌 값은 확정이 아닌 잠정안임
- 러너는 파이썬 패키지 `kyab_runner/`와 명령행 도구 `tools/`로 이루어지고, 판본은 `kyab_runner/__init__.py`의 `__version__`(0.1.0)임. KYAB는 문항 ID와 패키지 이름에 붙는 접두어이며, 신규 문항 ID는 `KYAB-` 뒤 숫자 6자리 꼴임
- 원칙은 같은 입력과 같은 조건이면 다시 돌려도 같은 기록이 나오게 하고, 모든 기록을 팀 공통 코드북 형식 그대로 남기며(열 이름·순서·허용값을 코드에 따로 적지 않음), 원천 데이터에서 납품 파일까지 ID와 판본으로 거슬러 올라갈 수 있게 하는 것임. 실행에 쓴 코드도 실행 코드 판본(`runner-0.1.0+<커밋 7자리>`, 커밋 안 된 수정이 있으면 끝에 `.dirty`)으로 04 `execution_library_version`에 남아 git 커밋으로 되짚을 수 있음(`kyab_runner/provenance.py`의 `library_version`)

## 2. 러너가 맡는 일

**러너의 일은 입력 검증부터 납품 변환까지 여섯 단계이며, 입력 검증은 나머지 다섯 단계의 명령이 시작할 때마다 먼저 돌고 오류가 하나라도 있으면 종료 코드 2로 멈춘다.**

| 단계 | 하는 일 | 진입점 | 쓰는 파일 |
|---|---|---|---|
| 입력 검증 | 01\~03을 코드북과 위험 분류체계로 검사함. 오류가 하나라도 있으면 모델을 부르지 않음 | `kyab_runner/validate.py`의 `validate_inputs`. 판정·사후 산출·집계·납품 변환은 공통 준비 `kyab_runner/context.py`의 `prepare`에서 부름. 따로 돌릴 때는 `run_single --validate-only` | 없음(화면 출력) |
| 모델 실행 | 사전 점검(모델 등록·호출 파라미터·서버 최대 길이 등) 뒤 문항 판본 × 모델 × 반복마다 실행 1건을 진행함 | `python -m kyab_runner.run_single`(단일턴), `python -m kyab_runner.run_multiturn`(3턴) | 04, 05, 배치 매니페스트(`batch_manifest.json`), 보조 로그(`runner_events.jsonl`), 빈 판정 틀(`06_judgments_template.csv`) |
| 판정 입출력 | 판정 입력 눈가림(모델을 알 수 있는 값을 뺌)을 거친 판정 입력을 만들고, 판정기[^judge]를 부르고, 06을 검증한 뒤 덧붙임. 사람 재채점 표본 20%를 표시함 | `python -m kyab_runner.run_judge` | 06, `judge_inputs.jsonl`, `judge_manifest.json` |
| 사후 산출 | 판정 결과로 04의 `first_fail_turn`·`first_cfc_turn`을 채움 | `tools/apply_judgments.py`(`python -m kyab_runner.apply_judgments`도 같음) | 04의 두 열(원본은 `04_runs.csv.bak-<시각>`으로 남김) |
| 지표 집계 | 06을 다시 검증하고 지표를 계산해 07을 씀 | `python -m kyab_runner.run_aggregate` | 07, 분모 보조표(`results_denominators.csv`), 집계 보조 기록(`results_notes.json`) |
| 납품 변환 | 01\~06을 납품 JSONL로 바꾸고 07 결과 폴더를 복사함. 코드북에서 만든 JSON Schema[^json-schema]로 검사하고 왕복 대조를 함 | `tools/export_jsonl.py` | `items.jsonl`, `responses/`, `judgments/`, `results/`, `schema/`, `sources.json`, `manifest.json` |

실행 순서대로 각 단계의 진입 명령과 남기는 파일을 찾아볼 수 있게 정리했다. 단계마다 진입점이 따로 있으므로 실행이 끝난 배치를 나중에 판정하거나, 여러 배치를 모아 한 번에 집계할 수 있다. 각 단계는 시작할 때 입력 3종을 실행 단계와 같은 규칙으로 다시 검증하므로, 실행 뒤에 고친 입력에 오류가 있으면 판정이나 집계 전에 멈춘다.

- 보조 도구는 로컬 vLLM 서버를 띄우고 끄고 상태를 확인하는 `tools/vllm_server.py`, 배치 안 반복 간 응답이 같은지 세는 결정성 점검 `tools/check_determinism.py`, xlsx 명세를 생성 모듈[^genmod]로 추출하는 `tools/extract_codebook.py`·`tools/extract_taxonomy.py`, 저장소 밖 원천 CSV에서 개발 샘플 01\~03을 다시 만드는 `tools/build_samples.py`, 종단 시험 스크립트 `tools/e2e_judge_aggregate.sh`와 그 결과 확인 `tools/e2e_check.py`임
- 단계별 입력·처리·출력은 [02 동작 흐름](02_동작_흐름.md), 명령·옵션·종료 코드는 [04 명령어 사용법](04_명령어_사용법.md), 설정 키 전체는 [05 설정 변수 사전](05_설정_변수_사전.md), 판정 규칙과 지표 정의는 [07 판정과 지표](07_판정과_지표.md), 용어 풀이는 [08 용어집](08_용어집.md)에 있음

## 3. 러너가 맡지 않는 일

**문항 제작, 위험 분류체계, 코드북과 지표 명세, 채점 규칙은 다른 부문이 만들고 러너는 받아서 검사하고 따르며, 아직 받지 못한 지표 명세와 채점 규칙은 잠정안이나 모의 판정기로 대신한다.**

| 맡지 않는 일 | 맡는 곳 | 러너와 만나는 자리 |
|---|---|---|
| 문항 제작(01·03 작성, 원천 문항의 번역·한국화) | 문항 제작 부문 | 입력 CSV 01·03. 러너는 검증만 하고 고치지 않음 |
| 위험 분류체계(위험군 A1\~A10, 소분류 39개)와 문항 태그(02) | 분류 담당 부문 | 분류체계 xlsx에서 추출한 생성 모듈 `kyab_runner/spec/taxonomy_data.py`와 입력 CSV 02 |
| 코드북(7 CSV의 열·허용값·형식) | 코드북 담당 | 코드북 xlsx에서 추출한 생성 모듈 `kyab_runner/spec/codebook_data.py`와 overlay[^overlay] |
| 지표 명세(분모, 판단 보류, 차단 처리) | 코드북 담당 | 규칙 파일 `config/aggregation_rules.yaml`. 명세 전에는 연구실 A 잠정안으로 채움 |
| 채점 규칙(루브릭 본문, 판정 프롬프트, 치명적 실패 코드 목록, 재채점 기준) | 채점 규칙 담당 | 판정기 등록부 `config/judges.yaml`과 `kyab_runner/judges/`. 받기 전이라 모의 판정기만 있음 |
| 독립 검증 | 연구실 B | 미정 |
| 문항 수량·비율 결정 | 연구책임자와 AISI 협의 | 입력 문항 수 |

러너 밖에서 정해지는 것과 그 결정이 들어오는 러너 쪽 파일을 한 줄씩 짝지었다. 오른쪽 열의 생성 모듈, overlay, 설정 파일이 다른 부문의 결정을 러너로 들여오는 자리다. 그래서 명세가 바뀌면 대부분 코드가 아니라 이 파일들을 바꾸고, 새 판정기나 새 공급자처럼 호출 방식이 늘어날 때만 코드를 더한다.

## 4. 기준 문서

**러너의 열 이름·순서·허용값은 모두 7 CSV 코드북 v0.2에서 오고, 코드북 v0.3이 오기 전에 확정된 변경은 overlay 한 파일에 따로 적는다.**

| 문서 | 정하는 것 | 러너 안의 위치 |
|---|---|---|
| 7 CSV 코드북 v0.2(xlsx) | 01\~07의 열 이름·순서·허용값·형식·필수 여부 | 생성 모듈 `kyab_runner/spec/codebook_data.py` |
| overlay | 코드북 담당 회신으로 확정된 변경과 잠정 가정 | `schema/overlay_v0.3_confirmed.yaml` |
| 위험 분류체계(xlsx) | 위험군 A1\~A10, 소분류 39개, 옛 코드 R1\~R5·M01\~M05 대응 | 생성 모듈 `kyab_runner/spec/taxonomy_data.py` |
| 수행계획서 v1.1 | 실행 조건(표 Ⅳ-20), 지표 정의(표 Ⅳ-22), 사람 재채점 20% | 규칙 파일과 설정 파일 주석이 근거로 가리킴 |

러너가 따르는 기준 문서마다 저장소 안 어디에 들어 있는지 적었다. xlsx 두 개는 저장소 밖에 있고, 저장소에는 그 추출본인 생성 모듈만 들어 있다. 코드북이 정하지 않은 판정·집계 결정은 기준 문서가 아니라 연구실 A 잠정안이며, 규칙 파일 `config/aggregation_rules.yaml`에 따로 모여 있다.

- 명세 로드(`kyab_runner/codebook.py`의 `load_codebook`)는 먼저 읽은 분류체계(`kyab_runner/taxonomy.py`의 `load_taxonomy`)를 받아 코드북 생성 모듈 위에 overlay를 덧씌운 명세 하나를 만들고, 검증·기록·스키마 생성(`validate.py`·`csv_io.py`·`export.py`)이 모두 이 명세를 씀. xlsx 없이 생성 모듈만으로 명세가 갖춰지므로 저장소만 받아도 러너가 돌아가며, 코드북이 바뀌면 추출기를 다시 돌려 생성 모듈을 새로 만듦([03 폴더와 모듈](03_폴더와_모듈.md) 4절)

### 4.1 7 CSV 코드북 v0.2

**코드북은 표 7개의 열을 정하며, 01\~03은 다른 부문이 만드는 입력이고 04\~07은 러너가 쓰거나 검증하는 기록이다.**

| 표 | 한 행의 단위 | 코드북 v0.2 필드 수 | 러너가 쓰는 열 수 | 만드는 쪽 |
|---|---|---|---|---|
| `01_items` | 문항 판본 1개(`item_id` + `item_version`) | 27 | 27 | 입력. 문항 제작 부문 |
| `02_item_tags` | 문항 판본의 태그 판본 1개 | 29 | 30 | 입력. 분류 담당 부문 |
| `03_prompts` | 턴 1개의 사용자 발화 | 7 | 7 | 입력. 문항 제작 부문 |
| `04_runs` | 실행 1건(문항 판본 × 모델 × 반복 번호) | 27 | 27 | 러너 모델 실행 단계 |
| `05_responses` | 턴 1개의 최종 응답 | 11 | 11 | 러너 모델 실행 단계 |
| `06_judgments` | 판정 1건 | 29 | 29 | 판정기와 사람. 러너가 검증하고 덧붙임 |
| `07_results` | 모델 × 슬라이스 1개 | 35 | 35 | 러너 지표 집계 단계 |

문서 전체에서 01\~07이라는 번호로 부르는 표가 각각 무엇인지 이 표에 정리했고, 열 하나하나의 뜻과 허용값은 [06 데이터 필드 사전](06_데이터_필드_사전.md)에 있다. 러너가 쓰는 열 수가 코드북과 다른 곳은 02 하나뿐이며, overlay가 대조 문항의 대상 위험군 열 `control_target_risk`를 더했기 때문이다. 다른 팀이 코드북 원본 머리글(02는 29열)로 만든 파일도 이 열만 빠진 경우에는 읽어 주고, 쓸 때는 항상 30열로 쓴다.

### 4.2 overlay와 2026-10-05 회신

**overlay는 코드북 v0.3이 오기 전까지 확정 변경과 잠정 가정을 상태로 구분해 담으며, 2026-10-05 코드북 담당 회신 4건은 모두 반영하고 회신이 정하지 않은 세부는 provisional로 남겼다.**

| 상태 | 뜻 | 항목 수 | 예 |
|---|---|---|---|
| confirmed | 코드북 담당 회신으로 확정된 변경 | 9 | `protocol_id` 표기를 `MT3-1.0.0` 꼴로 통일(OV-C1), 위험군 A1\~A10 단일 체계(OV-C5), 출력 한도 허용값 8192(OV-R1005-1), 치명적 실패 없음은 `NONE`(OV-R1005-3) |
| provisional | 회신이 정하지 않았으나 러너가 돌아가려면 값이 필요해 연구실 A가 둔 가정 | 8 | `control_target_risk`의 이름·위치·값 규칙(OV-P4), 차단·오류 응답의 빈 본문 허용(OV-P3), 해당 없는 루브릭 차원의 빈값 허용(OV-J3) |

overlay 항목 17개를 상태별로 나누고 대표 예를 붙였다. 코드는 두 상태의 항목을 똑같이 적용하므로, 어느 규칙이 잠정인지는 항목에 적힌 상태 값으로만 알 수 있다. 코드북 v0.3이 오면 추출기를 다시 돌리고 v0.3에 반영된 항목을 overlay에서 지운다.

- `load_codebook`이 적용한 항목 목록은 배치 매니페스트의 `codebook_overlays`에 남음. 열을 새로 넣는 `add_field` 항목은 `authorized_by`로 confirmed 항목을 가리켜야 하며, 없으면 명세 로드가 거부함. 2026-09-30 회신 1\~5는 OV-C 항목, 2026-10-05 회신 ①\~④는 OV-R1005 항목으로 적고, 항목 17개 전체는 [05 설정 변수 사전](05_설정_변수_사전.md) 8절에 있음

| 회신 | 요지 | 러너 반영 | provisional로 남은 세부 |
|---|---|---|---|
| ① | 출력 한도 상향(긴 응답이 절단되어 상담 안내 누락으로 판정되는 것 방지) | 출력 한도 1,024 → 8,192, 서버 최대 길이 32,768(OV-R1005-1) | 값 8,192는 연구실 A 결정. 수행계획서 v1.1 표 Ⅳ-20의 1,024와 달라 변경 기록이 필요함 |
| ② | 대조 문항이 어느 위험군의 대조인지 잇는 열 추가 | 02에 `control_target_risk` 추가, 위험군별 과잉거절률 산출(OV-R1005-2, OV-P4) | 열 이름·위치·값 규칙 |
| ③ | 치명적 실패가 없으면 빈칸 대신 `NONE` | 06 `critical_failure_code`에 `NONE` 기록, 판정이 끝난 행의 빈칸은 오류(OV-R1005-3) | `NONE`이 아닌 코드와 verdict 조합의 해석(OV-J1b) |
| ④ | 판단 보류는 허용하되, 실패율에서 빼면 건수·비율·분모를 함께 제시 | 분모 보조표와 집계 보조 기록에 분모·판단 보류 건수·판단 보류율 기록(OV-R1005-4) | 제시 형식과 분모 성분의 정의. 07 열 추가는 승인되지 않음 |

### 8.1 기동, 메모리, 속도

**Kanana-2-30B는 가중치가 커서 GPU 메모리 여유가 작지만 출력 속도는 Qwen3.8-27B의 약 3배다.**

| 모델 | 기동 시간 | 가중치 | KV 캐시[^kv-cache] | 32k 요청 동시 처리 | 출력 속도(대략) |
|---|---|---|---|---|---|
| Kanana-2-30B | 약 8.6분 | 57.13GiB | 11.66GiB(226,368 토큰) | 6.91배 | 약 150 토큰/초 |
| Qwen3.8-27B | 약 6.8분 | 51.1GiB | 18.73GiB(284,717 토큰) | 8.69배 | 약 49 토큰/초 |

본평가에 드는 GPU 시간과 메모리 여유를 가늠하는 근거로 실었다. Kanana-2-30B는 전문가 혼합[^moe] 구조로 활성 파라미터가 약 3B라서, 가중치가 더 커도 출력은 더 빠르다. 동시 처리 배수는 KV 캐시 토큰 수를 32,768로 나눈 값이지만 러너는 지금 한 번에 1건씩 보내므로, 출력 속도는 순차 호출 조건에서만 유효하다.

- Qwen3.8-27B는 기본 어텐션 백엔드[^attn-backend]가 작업 서버의 vLLM 가상환경에 든 torch 빌드와 맞지 않아 첫 계산에서 실패하므로 `--attention-backend TRITON_ATTN`을 쓰고, 기본 동시 시퀀스 수(1024)가 상태 캐시 블록 수를 넘어 기동이 거부되므로 `--max-num-seqs 64`로 낮춤. Kanana-2-30B는 MLA[^mla] 구조라 일반 어텐션 백엔드를 거부하므로 `--attention-backend TRITON_MLA`를 씀
- 서버 최대 길이를 32,768로 둔 까닭은 vLLM 0.30이 요청의 입력 상한을 서버 최대 길이에서 출력 한도를 뺀 값으로 잡아, 8,192로 두면 입력 상한이 0이 되어 모든 호출이 실패하기 때문임. 3턴 마지막 턴의 최악 입력은 약 17k 토큰이고, Kanana-2-30B는 위치 임베딩 상한이 32,768이라 더 올릴 수 없음

### 8.2 스모크

**공개 2종 × 단일턴·3턴 네 배치의 스모크[^smoke]가 모두 끝까지 돌았고, 절단과 04·05 코드북 위반은 0건이었다.**

| 모델 | 프로토콜 | 실행 수(문항 3 × 반복 3) | 실행 상태 | 절단 | 04·05 코드북 위반 | 최대 출력 토큰 |
|---|---|---|---|---|---|---|
| Kanana-2-30B | 단일턴 | 9 | 모두 completed | 0 | 0 | 156 |
| Kanana-2-30B | 3턴 | 9 | 모두 completed | 0 | 0 | 292 |
| Qwen3.8-27B | 단일턴 | 9 | 모두 completed | 0 | 0 | 657 |
| Qwen3.8-27B | 3턴 | 9 | 모두 completed | 0 | 0 | 1,019 |

출력 한도를 8,192로 올린 뒤에도 실행 경로가 끝까지 도는지 스모크로 확인했다. 가장 긴 응답도 1,019 토큰으로 출력 한도의 약 8분의 1이어서, 개발 샘플에서는 한도에 닿은 응답이 없었다. 개발 샘플 6문항의 결과라 본평가 문항에서는 응답 길이 분포가 달라질 수 있으며, 절단 건수는 실행 요약과 집계 보조 기록에 계속 남는다.

### 8.3 반복과 날짜 간 응답 일치

**같은 서버 설정 안에서는 두 모델 모두 3회 반복 응답이 글자 단위로 같았지만, Kanana-2-30B는 서버 최대 길이가 바뀌면 응답이 달라졌다.**

| 비교 | Qwen3.8-27B | Kanana-2-30B |
|---|---|---|
| 같은 배치 안 3회 반복(2026-10-05) | 12/12 턴 동일 | 12/12 턴 동일 |
| 샘플러 교체 전후(2026-09-30 대 2026-10-02) | 36/36 응답 동일 | 해당 없음(2026-09-30에는 실행하지 않음) |
| 출력 한도·서버 최대 길이 변경 전후(2026-10-02 대 2026-10-05) | 36/36 응답 동일 | 0/36 |

이 표는 같은 조건으로 다시 돌렸을 때 같은 응답이 나오는지, 곧 본평가 결과를 재현할 수 있는지 보여 준다. 마지막 줄에서 Kanana-2-30B만 0/36인데, 원인을 나눠 보니 출력 한도가 아니라 서버 최대 길이가 응답을 바꿨다. 따라서 서버 설정을 배치마다 기록하고 본평가 전에 고정해야 하며, 서버 설정이 다른 Kanana-2-30B 배치끼리는 응답을 비교하지 않는다.

- 12/12 턴은 개발 샘플의 턴 12개(단일턴 3개, 3턴 문항의 턴 9개) 모두에서 반복 1·2·3의 응답이 같았다는 뜻이고, 36/36은 턴 12개 × 반복 3회의 응답 수임. 같은 배치 안 반복 간 일치는 `tools/check_determinism.py`로 셈
- 2026-10-02 배치는 출력 한도 1,024, 서버 최대 길이 8,192 조건이었음. 원인을 나누려고 32,768 서버에 출력 한도 1,024로 보낸 응답은 2026-10-05 응답과 같았고, 서버를 8,192로 다시 띄워 2026-10-02 요청을 보낸 응답은 2026-10-02 응답을 36/36 재현했음. 서버 최대 길이는 배치 매니페스트의 `adapter_info`에 남음

## 9. 비용 추정

**상용 3종 본평가 비용은 판정 비용을 빼고 약 116달러로 예상하며, 상한은 약 400달러다.**

| 항목 | 값 |
|---|---|
| 대상 | 상용 3종(GPT-5.6 Terra, Claude Sonnet 4.6, Gemini 3.8 Flash). 공개 2종은 API 비용 없이 작업 서버의 GPU 시간만 씀 |
| 문항과 실행 수 | 540(위험 480 + 대조 60), 문항마다 3회 반복해 모델당 1,620실행. 수량·비율은 연구책임자와 AISI 협의 사항 |
| 예상 비용과 상한 | 약 116달러(실험·재실행 여유 포함), 상한 약 400달러 |
| 포함하지 않은 것과 단가 기준 | 판정 비용 제외, 단가는 2026-09-30 조사 |

상용 모델 실호출에 필요한 유료 집행 승인의 근거로 이 추정을 적어 둔다. 예상 비용과 상한 사이의 폭이 크고, 판정 비용은 어느 값에도 들어 있지 않다. 본평가 문항과 실제 판정기가 아직 정해지지 않아 두 값 모두 추정이며, 비용 칸은 코드북에 없으므로 실행 뒤에는 05 `raw_response_json`의 토큰 사용량(`usage`)과 단가로 다시 계산한다.

## 10. 남은 일

**본평가를 막고 있는 것은 상용 API 승인, 채점 규칙, 지표 명세, 본평가 문항이며, 러너는 각각을 받으면 붙일 자리를 갖춰 두고 기다린다.**

| 남은 일 | 기다리는 것 | 러너 쪽 현재 상태 |
|---|---|---|
| 상용 3종 실호출 | API 키, 유료 집행 승인, 외부 전송 조건 확인. 공식 API 모델 이름, 모델 판본 문자열, 추론 설정 확인 | 어댑터 3종과 가짜 응답 시험 완료. `enabled: false`로 막혀 있음 |
| 실제 판정기 | 채점 규칙(루브릭 본문), 판정 프롬프트, 치명적 실패 코드 목록 | 판정기 규격(`kyab_runner/judges/base.py`)과 모의 판정기뿐. 모의 판정이 섞이면 집계와 납품이 거부함 |
| 분모·판단 보류·차단 규칙 교체 | 지표 명세 확정(코드북 담당) | 규칙 파일에 연구실 A 잠정안. 규칙을 바꾸면 `aggregation_rule_version`(현재 0.2.3)을 올림 |
| 본평가 실행 | 본평가 문항(위험 480 + 대조 60) 수신. 수량·비율은 연구책임자와 AISI 협의 | 개발 샘플 6문항으로만 실행함 |
| Kanana-2-30B 서버 설정 고정 | 본평가 전에 정할 일 | `config/models.yaml`의 서버 최대 길이 32,768로 실행 중이며 배치 매니페스트에 기록됨 |
| 출처 역추적 빈칸 | 코드북 담당과 협의 | 원천 취득일, 번역·한국화 이력, 신규 문항 작성 근거, 대조 문항이 본뜬 위험 문항이 빈칸임. `sources.json`의 TODO와 집계 보조 기록의 협의 후보로 남김 |
| 납품 매니페스트의 수량·비율 분포표 자동 생성 | 제안 채택 여부 | 미구현 |
| 코드북 v0.3 이관 | 코드북 v0.3 xlsx 수령 | overlay로 운영 중. 받으면 추출기를 다시 돌리고 반영된 overlay 항목을 지움 |
| 출력 한도 변경 기록(수행계획서 v1.1 표 Ⅳ-20의 1,024와 다름) | 기록할 문서와 절차 미정 | `config/runner.yaml`과 overlay 주석에 필요성만 적혀 있음 |
| 사람 판정 적재 | 재채점 기준(채점 규칙 담당) | 적재 도구 없음. 사람 판정 행이 있으면 06 검증과 κ 계산은 동작함 |
| 임시 값 교체 | 지표 명세, 채점 규칙, 등록 코드 목록 | CRRI 임계값 0.25, 루브릭 판본 1.0.0, 치명적 실패 코드 자리표시 `CFC-MOCK-01`, 공개 모델 `provider` 값 `local_vllm`, 신규 문항 라이선스 코드 `LicenseRef-KYAB-internal`을 임시로 씀 |

남은 일마다 기다리는 대상과 러너 쪽 현재 상태를 적었다. 위 네 줄은 러너 밖에서 와야 해서 본평가를 직접 막고, 다섯째 줄은 본평가 전에 정할 일이며, 나머지는 결과를 보고하거나 납품하기 전에 정리하면 된다. 공개 2종 실행은 본평가 문항이 오고 Kanana-2-30B 서버 설정을 고정하면 시작할 수 있지만 그 판정과 집계는 채점 규칙과 지표 명세를 기다려야 하며, 지금까지 만든 07 수치는 모두 모의 판정기에서 나온 것이라 모델 평가 결과로 인용하지 않는다.

[^genmod]: 생성 모듈: 코드북·분류체계 xlsx에서 추출기가 자동으로 만든 파이썬 명세 모듈(`kyab_runner/spec/`). 손으로 고치지 않고, 원본이 바뀌면 추출기를 다시 돌림.

[^kv-cache]: KV 캐시: 모델이 앞서 읽은 토큰의 중간 계산값을 GPU 메모리에 담아 두는 공간. 클수록 긴 요청이나 많은 요청을 동시에 처리함.

[^attn-backend]: 어텐션 백엔드: vLLM에서 어텐션 계산을 맡는 커널 구현.
[^mla]: MLA(Multi-head Latent Attention): 키·값을 저차원으로 압축해 저장하는 어텐션 구조.
[^smoke]: 스모크: 본 실행 전에 적은 입력으로 전체 경로가 끝까지 도는지 보는 짧은 시험.
