## 1. 공통 사항

**모든 명령은 저장소 최상위 폴더에서 러너 가상환경의 파이썬(`.venv/bin/python`)으로 실행한다.**

- 진입점은 패키지 모듈(`-m kyab_runner.<이름>`)과 도구 스크립트(`tools/<이름>.py`) 두 형태이고, 모두 `-h`/`--help`로 옵션 목록을 보여 줌. 사후 산출은 `tools/apply_judgments.py`와 `python -m kyab_runner.apply_judgments`, 납품 변환은 `tools/export_jsonl.py`와 `python -m kyab_runner.export` 두 이름으로 실행할 수 있고 옵션이 같음
- `--input`·`--out`·`--rules`의 기본값은 현재 폴더가 아니라 저장소 최상위 폴더 기준 경로임(`kyab_runner/paths.py`). 명령줄에 직접 준 상대 경로는 현재 폴더 기준으로 해석함
- 한 출력 루트[^outroot]에 실행기 두 개를 동시에 돌리지 않음. 실행 ID 발급이 겹칠 수 있음

### 1.1 다른 환경에서 바꿀 값

**작업 서버[^server]에 묶인 값은 `config/runner.yaml`의 vLLM[^vllm] 관련 경로 네 개와, 저장소 바깥을 가리키는 기본 위치 두 곳이다.**

| 값 | 정의 위치 | 현재 값 | 쓰는 명령 | 다른 환경에서 |
|---|---|---|---|---|
| `vllm_venv` | `config/runner.yaml` | `<작업 폴더>/.venvs/etri-vllm` | `tools/vllm_server.py start` | 바꿀 값. 경로에 공백이 없는 vLLM 전용 가상환경(만드는 법은 6.6) |
| `hf_home` | `config/runner.yaml` | `<작업 폴더>/.cache/huggingface` | `tools/vllm_server.py start` | 바꿀 값. 모델 스냅샷이 있는 캐시 위치. 환경변수 `HF_HOME`이 있으면 그 값이 우선 |
| `vllm_env.FLASHINFER_WORKSPACE_BASE` | `config/runner.yaml` | `<작업 폴더>` | `tools/vllm_server.py start` | 바꿀 값. 서버 프로세스에 넘기는 환경변수 |
| `vllm_env.VLLM_CACHE_ROOT` | `config/runner.yaml` | `<작업 폴더>/.cache/vllm` | `tools/vllm_server.py start` | 바꿀 값. 서버 프로세스에 넘기는 환경변수 |
| 원천 CSV 폴더 | `kyab_runner/paths.py` `DEFAULT_DATA_DIR` | 저장소 밖 `../data/` | `tools/build_samples.py`, `tools/export_jsonl.py` | 샘플 생성은 `--data-dir`로 지정함. 납품 변환은 옵션이 없어, 폴더가 없으면 `sources.json`의 판본·위치를 비우고 경고만 냄 |
| 명세 xlsx 폴더 | `tools/_xlsx_common.py` `DEFAULT_SRC_DIR` | 저장소 밖 `../project proposal/` | `tools/extract_codebook.py`, `tools/extract_taxonomy.py` | `--xlsx`로 파일 경로를 줌 |

공유 저장소를 다른 서버에 받으면 이 여섯 값부터 확인한다. 앞의 네 줄(`<작업 폴더>`는 작업 서버의 작업 폴더 경로이며 실제 값은 `config/runner.yaml`에 있음)은 공개 모델 서버를 띄울 때만 읽히므로(`kyab_runner/config.py`는 이 키를 도구 전용 선택 키로 둠), 모의 모델[^mock]로 실행·판정·집계·납품만 할 때는 고치지 않아도 된다. 뒤의 두 줄은 평가 데이터와 명세 원본을 저장소에 넣지 않아서 생긴 값이며, 저장소만 받은 환경에서는 원천 CSV와 xlsx가 없는 상태가 기본이다.

## 2. 명령 한눈에 보기

**명령은 입력 준비, 실행, 판정, 사후 산출, 집계, 납품 변환 순서로 이어지고 단계마다 따로 실행한다.**

| 명령 | 하는 일 | 읽는 것 | 쓰는 것 | 필요한 자원 |
|---|---|---|---|---|
| `python -m kyab_runner.run_single` | 단일턴 실행 | 입력 3종(01·02·03), 설정 | 배치[^batch] 폴더(04·05·배치 매니페스트[^manifest]·보조 로그·판정 틀) | 모의 모델이면 없음, 공개 모델이면 GPU 서버, 상용 모델이면 API(현재 막힘) |
| `python -m kyab_runner.run_multiturn` | 다중턴(MT3·MT7·MT10) 실행 | 입력 3종, 설정 | 배치 폴더 | run_single과 같음 |
| `python -m kyab_runner.run_judge` | 판정 입력 생성, 판정, 06 검증·기록 | 배치, 입력 3종, 규칙 파일 | `judge_inputs.jsonl`, `06_judgments.csv`, `judge_manifest.json` | 없음(등록된 판정기는 모의 판정기[^mockjudge]뿐) |
| `tools/apply_judgments.py` | 04의 `first_fail_turn`·`first_cfc_turn` 채우기 | 배치(04·05·06), 입력 3종 | `04_runs.csv`의 두 열, 백업 `04_runs.csv.bak-<시각>` | 없음 |
| `python -m kyab_runner.run_aggregate` | 지표 집계 | 배치(04·05·06), 입력 3종, 규칙 파일 | 결과 폴더(07·분모 보조표·집계 보조 기록) | 없음 |
| `tools/export_jsonl.py` | 납품 JSONL 변환과 검증 | 배치, 입력 3종, 결과 폴더(선택) | 납품 폴더 | 없음 |
| `tools/vllm_server.py` | 로컬 vLLM 서버 기동·종료·상태 확인 | `config/models.yaml`, `config/runner.yaml` | `var/vllm_server.json`, `var/vllm_server.log` | start만 GPU 1장 |
| `tools/check_determinism.py` | 반복 간 응답 동일 여부 확인 | 배치(04·05) | 없음(화면 출력) | 없음 |
| `tools/build_samples.py` | 개발 샘플 입력 6문항 생성 | 원천 CSV | 입력 3종 | 없음 |
| `tools/extract_codebook.py` | 코드북[^codebook] xlsx를 생성 모듈로 옮김 | 코드북 xlsx | `kyab_runner/spec/codebook_data.py` | 없음 |
| `tools/extract_taxonomy.py` | 분류체계 xlsx를 생성 모듈로 옮김 | 분류체계 xlsx | `kyab_runner/spec/taxonomy_data.py` | 없음 |
| `tools/e2e_judge_aggregate.sh` | 모의 배치 4개로 실행부터 결과 확인까지 돌리는 종단 시험 | 샘플 입력, 규칙 파일 | `var/e2e_task6/`(바꿀 수 있음) | 없음 |
| `tools/e2e_check.py` | 종단 시험의 결과 확인 단계 | 종단 시험 폴더 | 없음(화면 출력) | 없음 |

명령마다 맡은 일과 입출력을 한 줄씩 줄여 두었고, 단계 사이의 파일 흐름 그림은 [동작 흐름 1절](02_동작_흐름.md#1-전체-흐름)에 있다. 모델이나 GPU가 필요한 명령은 실행기 두 개와 서버 도구의 start뿐이고, 나머지는 기록된 CSV와 설정, 시작할 때 읽는 생성 모듈[^spec]만으로 서버 없이 돌므로 판정·집계·납품 경로는 모의 모델 배치로 어느 환경에서든 시험할 수 있다. 집계는 사후 산출이 채우는 두 열을 읽지 않아 둘의 순서는 묶여 있지 않고, 사후 산출을 납품 변환 전에 해 두면 납품 파일에 `first_fail_turn`·`first_cfc_turn` 값이 들어간다.

## 3. 진입점별 옵션

**진입점마다 사용 형식과 옵션 표를 두었고, 모든 파이썬 진입점에 공통인 `-h`/`--help`는 표에서 뺐다.**

### 3.1 실행기: run_single, run_multiturn

**두 실행기는 옵션이 같고, 기본 프로토콜[^protocol]과 받아들이는 대화 방식만 다르다.**

```bash
.venv/bin/python -m kyab_runner.run_single    [옵션]   # 기본 ST1-1.0.0, 단일턴 프로토콜만 실행
.venv/bin/python -m kyab_runner.run_multiturn [옵션]   # 기본 MT3-1.0.0, 다중턴 프로토콜만 실행
```

| 옵션 | 뜻 | 기본값 | 비고 |
|---|---|---|---|
| `--input` | 입력 3종(`01_items.csv`·`02_item_tags.csv`·`03_prompts.csv`) 폴더 | `samples/input` | 파일이 없으면 종료 2 |
| `--out` | 출력 루트. 아래에 `<run_batch_id>/` 폴더가 생김 | `samples/output` | git 제외 폴더 |
| `--model` | `config/models.yaml`의 `model_id` | `mock-echo` | 등록되지 않았거나 `enabled: false`면 종료 2 |
| `--protocol` | 실행할 `protocol_id` | run_single은 `ST1-1.0.0`, run_multiturn은 `MT3-1.0.0` | 실행기의 대화 방식과 다르면 종료 2. `MT7-1.0.0`·`MT10-1.0.0`은 run_multiturn으로 실행 |
| `--rollouts` | 문항당 반복 횟수 | `config/runner.yaml`의 `default_rollouts`(현재 3) | 0이나 생략은 기본값. 코드북 04 `rollout_no` 허용값(1\~3) 밖이면 종료 2 |
| `--items` | 실행할 `item_id`를 쉼표로 나열 | 프로토콜에 맞는 전체 문항 | 앞뒤 공백 제거. 그 문항의 모든 `item_version`이 선택됨. 01에 없는 ID는 경고만 냄. 쉼표·공백뿐이면 전체 실행으로 읽지 않고 종료 2 |
| `--batch-id` | 이어 쓸 `run_batch_id` | 없음(새 배치) | 형식 `RBATCH-YYYYMMDD-###`. `--out` 아래 그 폴더에 `batch_manifest.json`이 있어야 함 |
| `--allow-unverified` | 검토 미통과·비활성 문항도 실행 | 꺼짐 | 개발 샘플은 모두 `pending`·`quarantined`라 이 옵션이 필요함 |
| `--validate-only` | 입력 3종 검증과 `run_params` 점검만 하고 끝냄 | 꺼짐 | 모델 호출·폴더 생성 없음 |
| `--mock-scenario` | 모의 모델의 기본 시나리오 | `normal` | `normal`, `refusal`, `length`, `blocked`, `empty`, `error`, `timeout`, `flaky` 중 하나. `--mock-plan`을 주면 쓰지 않음 |
| `--mock-plan` | 호출별 시나리오를 정한 모의 계획 YAML | 없음 | 예: `samples/mock_plan_failures.yaml`. 규칙 조건 키는 `item_id`·`turn_index`·`rollout_no`이고, `max_model_len` 키를 두면 서버 최대 길이 점검을 시험할 수 있음 |

실행 명령에서 바꿀 수 있는 값은 위 열한 개가 전부다. 개발 샘플을 돌릴 때는 `--allow-unverified`가 꼭 필요하고, 실제 문항을 돌릴 때는 이 옵션 없이 검토를 통과한(`verified`·`revised`, `active`) 문항만 실행된다. temperature·top_p·출력 한도 같은 호출 파라미터는 옵션이 아니라 `config/runner.yaml`의 `run_params`에 있으므로, 명령줄 실수로 배치마다 조건이 달라지는 일은 생기지 않는다.

- 실행기는 입력 3종을 검증한 뒤 문항을 고르고, 모델을 부르기 전에 사전 점검[^preflight]을 함. 모델 등록, `run_params`의 코드북 04 허용값, `--rollouts`·`--batch-id`, 어댑터 생성(API 키, vLLM 서버, 모의 계획 파일, 모의 시나리오), 서버 최대 길이 가운데 하나라도 걸리면 배치 폴더와 번호를 만들지 않고 종료 2임. 서버 최대 길이 조건(`max_model_len - 출력 한도 >= (턴 수 - 1) × 출력 한도 + context_reserve_tokens`) 때문에 현재 설정(32,768, 8,192, 1,024)에서는 공개 모델의 MT7·MT10 실행이 거부되며, 프로토콜별 계산 표는 [동작 흐름 3.3절](02_동작_흐름.md#33-사전-점검)에 있음

### 3.2 판정 실행기: run_judge

**판정 실행기는 배치 폴더를 하나 이상 받아 판정 입력을 만들고 판정기를 부른 뒤, 06 전체를 검증해 문제가 없을 때만 덧붙인다.**

```bash
.venv/bin/python -m kyab_runner.run_judge [옵션] <배치 폴더> [<배치 폴더> ...]
```

| 옵션 | 뜻 | 기본값 | 비고 |
|---|---|---|---|
| `배치 폴더`(위치 인자) | 판정할 배치 폴더(`…/RBATCH-YYYYMMDD-###`) | 없음(1개 이상 필수) | 배치 기록이 입력 3종과 이어지지 않으면 종료 2 |
| `--input` | 입력 3종 폴더 | `samples/input` | 실행 때 쓴 입력을 줌 |
| `--judge` | `config/judges.yaml`의 `judge_id` | `mock-judge` | 현재 등록된 판정기는 `mock-judge`뿐. 미등록이면 종료 2. `--inputs-only`·`--validate-only`에서는 쓰지 않음 |
| `--inputs-only` | `judge_inputs.jsonl`만 만들고 끝냄 | 꺼짐 | `--validate-only`와 함께 쓸 수 없음(argparse 오류, 종료 2) |
| `--validate-only` | 이미 있는 `06_judgments.csv`를 검증만 함 | 꺼짐 | 06이 비어 있는 배치가 있으면 종료 1. 검증 오류가 있는 배치가 함께 있으면 종료 2 |

판정 실행기는 같은 판정기가 같은 태그 판본으로 이미 판정한 판정 자리를 건너뛰므로, 끊긴 뒤 다시 실행하면 빠진 자리만 채운다. 다만 새로 쓴 판정이 하나도 없을 때의 종료 코드는 1이며, 다시 실행해서 나온 1은 오류가 아니라 할 일이 없었다는 뜻이다. 모의 판정기로 만든 06에는 검증 경고가 붙고, 집계와 납품 변환도 같은 기준(`config/judges.yaml`의 `production: false`)으로 모의 판정을 찾아 거부한다.

### 3.3 사후 산출: tools/apply_judgments.py

**사후 산출 도구는 `04_runs.csv`의 `first_fail_turn`·`first_cfc_turn` 두 열만 채우며, 준 배치가 모두 검사를 통과해야만 쓴다.**

```bash
.venv/bin/python tools/apply_judgments.py [--input 입력 폴더] [--dry-run] <배치 폴더> [...]
.venv/bin/python -m kyab_runner.apply_judgments ...   # 같은 진입점, 옵션도 같음
```

| 옵션 | 뜻 | 기본값 | 비고 |
|---|---|---|---|
| `배치 폴더`(위치 인자) | 두 열을 채울 배치 | 없음(1개 이상 필수) | 여러 개를 주면 전부 검사한 뒤 모두 통과할 때만 씀 |
| `--input` | 입력 3종 폴더 | `samples/input` | |
| `--dry-run` | 계산과 검사만 하고 쓰지 않음 | 꺼짐 | 통과하면 배치별 건수를 출력하고 종료 0 |

이 도구가 멈추는 경우는 06이 없거나 검증 오류가 있을 때, 두 열에 이미 값이 있을 때, 주 판정 집합에 판정이 없는 성공 응답이 있을 때, 채운 행이 코드북 검사를 통과하지 못할 때다. 쓰기 전에 원본을 `04_runs.csv.bak-<YYYYMMDDTHHMMSS>`로 복사하므로, 잘못 채웠으면 이 백업으로 `04_runs.csv`를 되돌린 뒤 다시 실행한다. 두 열에 값이 하나라도 채워진 배치에 다시 실행하면 이미 값이 있다는 이유로 멈추고 종료 2를 돌려주며, 채울 값이 하나도 없던 배치(실패·치명적 실패가 없는 배치)는 같은 빈값을 다시 쓰고 백업만 하나 더 남긴다.

### 3.4 집계 실행기: run_aggregate

**집계 실행기는 배치 하나 이상을 묶어 지표를 계산하고, 실행할 때마다 기존 결과를 건드리지 않고 새 결과 폴더를 만든다.**

```bash
.venv/bin/python -m kyab_runner.run_aggregate [옵션] <배치 폴더> [...]
```

| 옵션 | 뜻 | 기본값 | 비고 |
|---|---|---|---|
| `배치 폴더`(위치 인자) | 집계할 배치 | 없음(1개 이상 필수) | 06이 없거나 비어 있는 배치가 있으면 종료 2 |
| `--input` | 입력 3종 폴더 | `samples/input` | |
| `--out` | 결과 폴더를 만들 출력 루트 | 배치 폴더들의 상위 폴더(모두 같아야 함) | 배치의 상위 폴더가 서로 다르면 이 옵션이 필요함(없으면 종료 2) |
| `--rules` | 규칙 파일 | `config/aggregation_rules.yaml` | 규칙을 바꿔 비교할 때 복사본을 줌. 준 경로와 파일 sha256이 `results_notes.json`에 남음 |
| `--allow-mock-judge` | 본평가에 쓸 수 없는 판정기(모의)의 판정으로도 집계 | 꺼짐 | 경로 확인용. 없으면 모의 판정이 섞인 집계를 종료 2로 거부 |

결과 폴더 이름은 `RESULTS-YYYYMMDD-###`이며 같은 날짜 안에서 집계할 때마다 번호가 하나씩 오르고, 강제 종료로 남은 임시 폴더(`RESULTS-*.tmp-*`)는 주의만 내고 지우지 않으므로 확인 뒤 직접 지운다. 같은 모델 묶음에 temperature·top_p·max_output_tokens가 다른 배치가 섞이면 집계를 거부하므로, 출력 한도가 다른 배치(예: 1,024와 8,192)는 따로 집계한다. `--rules`로 다른 파일을 줄 때는 `aggregation_rule_version`을 올려 두어야 07만 보고도 규칙을 구분할 수 있고, 판본을 올렸는지는 코드가 검사하지 않아 사람이 챙긴다.

### 3.5 납품 변환: tools/export_jsonl.py

**납품 변환은 코드북 CSV를 JSONL 납품 폴더로 바꾸고, 스키마 검증과 왕복 대조까지 끝낸다.**

```bash
.venv/bin/python tools/export_jsonl.py [<배치 폴더> ...] --out <납품 폴더> [--input 입력 폴더] [--results 결과 폴더] [--allow-mock-judge]
.venv/bin/python -m kyab_runner.export ...        # 같은 진입점, 옵션도 같음
```

| 옵션 | 뜻 | 기본값 | 비고 |
|---|---|---|---|
| `배치 폴더`(위치 인자) | 내보낼 배치 | 없음 | 없으면 `items.jsonl`·`schema/`·`sources.json`·`manifest.json`만 만듦 |
| `--out` | 납품 폴더 | 없음(필수) | 없거나 비어 있는 폴더여야 함 |
| `--input` | 입력 3종 폴더 | `samples/input` | |
| `--results` | 함께 넣을 결과 폴더 | 없음 | `07_results.csv`·`results_denominators.csv`·`results_notes.json`을 `results/`로 복사. 폴더나 파일이 없으면 주의만 내고 계속함 |
| `--allow-mock-judge` | 모의 판정이 섞여 있어도 내보냄 | 꺼짐 | 없으면 종료 2. 쓰면 `manifest.json`에 모의 판정 사용이 표시됨 |

납품 변환은 06 검증, 모의 판정, 호출 파라미터 섞임, ID 중복(같은 배치를 두 번 주거나 다른 출력 루트의 배치를 섞은 경우), `model_id` 파일 이름 규칙을 쓰기 전에 검사해, 여기서 걸리면 폴더를 만들지 않는다. 쓰는 도중 예외가 나거나 API 키·토큰으로 보이는 문자열이 나오면 납품 폴더를 지우고, 스키마 위반이나 왕복 차이로 끝나면 원인을 보도록 폴더를 남긴 채 종료 2를 돌려준다(단계별 처리는 [동작 흐름 6.2절](02_동작_흐름.md#62-처리-순서와-실패-처리)). 마지막 줄의 `스키마 위반 0 | 왕복 차이 0`이 납품해도 되는지 판단하는 기준이다.

### 3.6 로컬 서버 도구: tools/vllm_server.py

**서버 도구의 하위 명령은 start·stop·status 세 개이고, GPU를 쓰는 것은 start뿐이다.**

```bash
.venv/bin/python tools/vllm_server.py start --model <model_id> [--gpu 번호]   # GPU 필요
.venv/bin/python tools/vllm_server.py status
.venv/bin/python tools/vllm_server.py stop
```

| 하위 명령 | 옵션 | 뜻 | 기본값 | 비고 |
|---|---|---|---|---|
| `start` | `--model` | `config/models.yaml`의 `local_vllm` 모델 ID | 없음(필수) | 어댑터가 `local_vllm`이 아니면 종료 2. `enabled` 값은 보지 않음 |
| `start` | `--gpu` | 쓸 GPU 번호(1장) | `0` | 서버 프로세스의 `CUDA_VISIBLE_DEVICES`로 넘김 |
| `stop` | 없음 | 기록된 서버 프로세스 묶음을 종료 | | SIGTERM 뒤 60초 안에 끝나지 않으면 SIGKILL. 기록이 없어도 종료 0 |
| `status` | 없음 | 기록된 서버의 생존·준비 상태 출력 | | 기록이 없거나 준비되지 않았으면 종료 1 |

start는 서버를 띄우기 전에 이미 떠 있는 서버, HF 캐시의 해당 판본 스냅샷, vLLM 가상환경(있는지, 경로에 공백이 없는지), vLLM·torch·CUDA 판본을 차례로 확인하고, 하나라도 맞지 않으면 아무것도 띄우지 않고 종료 2로 끝난다. 서버는 `127.0.0.1`에만 묶이고 HF Hub 접속과 사용 통계 전송을 끈 환경변수로 뜨며, 준비될 때까지 최대 900초(`STARTUP_TIMEOUT_S`) 기다린다. 기동 정보는 `var/vllm_server.json`에 남고, 실행기의 로컬 어댑터(`kyab_runner/adapters/local_vllm.py`)는 그 기록의 모델 판본(revision)과 포트가 자기 설정과 같을 때만 이 내용을 `batch_manifest.json`의 `adapter_info.server`로 옮겨 적는다.

### 3.7 도구 스크립트: 결정성 점검, 샘플 생성, 명세 추출기

**결정성 점검, 샘플 생성, 명세 추출기는 모델을 부르지 않는 도구이며, 결과가 기대와 다르면 파일을 쓰지 않고 종료 코드로 알린다.**

```bash
.venv/bin/python tools/check_determinism.py <배치 폴더> [<배치 폴더> ...]
.venv/bin/python tools/build_samples.py [--data-dir 원천 CSV 폴더] [--out 출력 폴더]
.venv/bin/python tools/extract_codebook.py  [--xlsx 코드북 xlsx] [--out 생성 모듈 경로]
.venv/bin/python tools/extract_taxonomy.py [--xlsx 분류체계 xlsx] [--out 생성 모듈 경로]
```

| 도구 | 옵션 | 뜻 | 기본값 | 비고 |
|---|---|---|---|---|
| `check_determinism.py` | `배치 폴더`(위치 인자) | 비교할 배치 | 없음(1개 이상 필수) | 없는 폴더, 깨진 CSV, 04에 짝이 없는 05 행이 있으면 그 배치는 읽지 못한 것으로 보고 종료 2 |
| `build_samples.py` | `--data-dir` | 원천 CSV 폴더 | 저장소 밖 `../data/` | 원천 두 종의 CSV가 있어야 함. 파일 이름은 `config/sources.yaml`의 `local_file` |
| `build_samples.py` | `--out` | 01·02·03을 쓸 폴더 | `samples/input` | 같은 이름의 파일을 덮어씀 |
| `extract_codebook.py` | `--xlsx` | 코드북 xlsx 경로 | 저장소 밖 `../project proposal/`에서 파일 이름에 `codebook_v<CODEBOOK_VERSION>`이 든 xlsx | 판본은 스크립트 상수 `CODEBOOK_VERSION`(현재 `"0.2"`) |
| `extract_codebook.py` | `--out` | 생성할 모듈 경로 | `kyab_runner/spec/codebook_data.py` | |
| `extract_taxonomy.py` | `--xlsx` | 분류체계 xlsx 경로 | 같은 폴더에서 파일 이름에 `벤치마크비교와_재분류`가 든 xlsx | |
| `extract_taxonomy.py` | `--out` | 생성할 모듈 경로 | `kyab_runner/spec/taxonomy_data.py` | |

세 도구의 옵션을 한 표에 모았다. 결정성 점검은 배치마다 같은 문항·턴의 반복별 응답 본문이 글자 단위로 같은지 세고, 샘플 생성은 실제 평가 문항이 아닌 개발용 6문항(ID 900000번대)을 코드북 01·02·03 형식으로 쓰며, 두 추출기는 xlsx 원본을 기계적으로 옮겨 생성 모듈을 다시 만든다. 어느 도구도 조건이 어긋나면 기존 기록이나 생성 모듈을 고치지 않으므로, 기록과 원본이 그대로인지 확인하는 데 쓸 수 있다.

- 결정성 점검은 줄마다 문항·턴, 반복 횟수, 서로 다른 응답 가짓수, 응답 길이를, 배치 끝에 동일·다름 개수를 출력함. 다중턴에서는 처음 갈린 턴이 원인이고 그 뒤 턴은 입력이 이미 달라서 갈렸을 수 있으며, 차단·오류·빈 응답도 본문으로 비교해 섞여 있으면 다름으로 셈. 기록은 고치지 않고 하나라도 다르면 종료 1임
- 샘플 생성은 원천 CSV가 저장소에 없으므로 저장소만 받은 환경에서 `원천 원본을 읽을 수 없습니다`로 종료 2가 됨. 쓰기 전에 실행기와 같은 입력 검증을 돌려 경고가 하나라도 있으면 쓰지 않고(오류만 막는 실행기보다 엄격함), 시각 값이 상수라 같은 원본이면 저장소의 `samples/input`과 바이트 단위로 같은 파일이 나옴
- 코드북 추출기는 시트마다 선언된 필드 수와 읽은 필드 수를, 분류체계 추출기는 21개 검산 항목을 확인해 어긋나면 모듈을 쓰지 않고 종료 1임. xlsx를 찾지 못하거나 머리글 행이 없으면 오류 출력(stderr)에 한 줄을 남기고 종료 2임. 내용이 기존 모듈과 같으면 `변경 없음`을 출력하고 다시 쓰지 않으며, `--xlsx`로 준 파일은 이름의 판본을 검사하지 않으므로 코드북 새 판은 `CODEBOOK_VERSION`을 먼저 고쳐야 생성 모듈에 올바른 판본이 적힘

### 3.8 시험: 종단 시험과 단위 테스트

**종단 시험은 모의 배치 4개를 새로 만들어 판정, 사후 산출, 두 정책의 집계, 결과 확인까지 한 번에 돌리고, 단위 테스트는 서버·GPU·네트워크 없이 돈다.**

```bash
bash tools/e2e_judge_aggregate.sh [<실모델 배치 폴더> ...]                     # 종단 시험
.venv/bin/python tools/e2e_check.py <시험 폴더> <현재 규칙 판본> <비교 규칙 판본> [--input 입력 폴더]   # 결과 확인만
.venv/bin/python -m unittest discover -s tests                                        # 단위 테스트 전체
KYAB_UPDATE_GOLDEN=1 .venv/bin/python -m unittest discover -s tests -p test_golden.py # 골든 테스트 기준값 갱신(의도한 출력 변경일 때만)
```

| 종단 시험 입력 | 뜻 | 기본값 | 비고 |
|---|---|---|---|
| 위치 인자 | 함께 넣을 실모델 배치 | 없음 | 시험 폴더로 복사해서 쓰고, 끝에 원본 CSV의 md5가 그대로인지 확인함 |
| 환경변수 `E2E_DIR` | 시험 폴더 | `var/e2e_task6` | 시작할 때 지우고 새로 만듦. `var/` 밖의 폴더는 이 스크립트가 남기는 표지 파일 `.e2e_judge_aggregate`가 있을 때만 지우고, 없으면 `지울 수 없는 폴더입니다`로 종료 1. 처음 쓰는 폴더는 `mkdir -p <폴더> && touch <폴더>/.e2e_judge_aggregate`로 표지를 먼저 둠 |
| 환경변수 `E2E_SOURCE_BATCHES` | 위치 인자가 없을 때 넣을 실모델 배치(공백 구분) | 없음 | |

시험 단계는 원본 복사, 모의 배치 4개(정상 ST1·MT3, 실패 계획 ST1·MT3), 판정, 06 검증, 사후 산출, 집계(모의 판정 거부 확인 뒤 허용), 차단 정책을 `exclude`로 바꾼 비교 집계, `tools/e2e_check.py` 결과 확인 순서다. 비교용 규칙 파일은 판본의 PATCH 자리를 하나 올린 복사본으로 시험 폴더 안에 만들어져, 저장소의 `config/aggregation_rules.yaml`은 바뀌지 않는다. 스크립트가 `--input`을 넘기지 않아서 인자로 주는 배치는 `samples/input`으로 실행한 배치여야 하고, 출력 한도 1,024로 기록된 옛 배치는 코드북 04 허용값(8192)에 맞지 않아 사후 산출 단계에서 거부된다.

- `e2e_check.py`는 06 완료 행의 `critical_failure_code` 빈칸 0, 06 검증 오류 0, 결과 폴더 2개, 07 코드북 위반 0, 07 결과 검증(`metrics.validate_results`) 문제 0, 분모 보조표 행과 07의 `result_id` 1:1, `risk_group` 슬라이스 행의 `over_refusal_rate` 값 존재, 분모 불변식, 규칙 판본 순서를 확인함
- 골든 테스트[^golden]를 모듈 이름(`python -m unittest tests.test_golden`)으로 부르면 `tests/` 안의 공용 모듈 `support`를 찾지 못해 실패함. `tests/test_golden.py` 머리 주석과 같은 `discover -s tests -p test_golden.py` 형태를 씀
- 저장소 밖 원본이 없으면 단위 테스트 3개(명세 추출기 재현성 2개는 `../project proposal/`의 xlsx, 샘플 재생성 1개는 `../data/`의 원천 CSV)를 건너뜀. 기준값 갱신·출력 덤프(`KYAB_UPDATE_GOLDEN`·`KYAB_GOLDEN_DUMP`)를 켜지 않으면 테스트는 파이썬 `tempfile` 규칙(환경변수 `TMPDIR`)의 임시 폴더에만 씀

## 4. 종료 코드

**종료 코드의 기본 약속은 `kyab_runner/exitcodes.py`의 0·1·2·130이지만, 1의 뜻은 실행기·판정·집계와 도구 스크립트에서 서로 다르다.**

| 진입점 | 0 | 1 | 2 | 그 밖 |
|---|---|---|---|---|

첫 줄은 상수 이름이 정한 기본 뜻이고, 그 아래는 같은 숫자가 진입점마다 무엇을 뜻하는지 한 줄씩 대조한 것이다. 실행기·판정·집계에서 1은 오류 없이 할 일이 없었다는 뜻이라 다음 단계로 넘어가도 되지만 결정성 점검, 서버 도구, 명세 추출기, 종단 시험에서는 실패를 뜻하므로(이 도구들도 입력·설정 오류에는 2), 스크립트로 단계를 이을 때는 1을 따로 다루고 판정 재실행·서버 상태 확인·결정성 점검의 1을 한데 묶지 않는다. 130을 직접 돌려주는 진입점은 실행기 두 개뿐이며(다른 명령은 Ctrl-C에 파이썬 기본 동작으로 멈춤), 이때는 화면에 나온 `--batch-id` 안내대로 이어 쓰면 된다.

- 명령줄 옵션을 잘못 주면(필수 인자 누락, 모르는 옵션, 함께 쓸 수 없는 옵션) argparse가 사용법을 출력하고 모든 파이썬 진입점에서 2로 끝남
- 판정, 사후 산출, 집계, 납품 변환, `e2e_check.py`는 같은 준비 절차(`kyab_runner/context.py`의 `prepare`)로 시작함. 배치 매니페스트가 잘렸거나 필수 키(`run_batch_id`·`protocol_id`)가 없으면 `배치 또는 입력을 읽을 수 없습니다` 한 줄과 함께 종료 2임

## 5. 명령이 읽는 환경변수

**명령이 직접 읽는 환경변수는 여섯 종류이고, 판정·사후 산출·집계·납품 변환은 환경변수를 읽지 않는다.**

- 서버 도구 start의 `HF_HOME`(`config/runner.yaml`의 `hf_home`보다 우선), 실행기의 상용 API 키 `OPENAI_API_KEY`·`ANTHROPIC_API_KEY`·`GEMINI_API_KEY`(변수 이름은 `config/models.yaml`의 `api_key_env`), 골든 테스트의 `KYAB_UPDATE_GOLDEN`(`1`이면 기준값 갱신)·`KYAB_GOLDEN_DUMP`(정규화한 출력을 남길 폴더), 종단 시험의 `E2E_DIR`·`E2E_SOURCE_BATCHES`임. 실행 결과에 영향을 주는 값은 `HF_HOME`과 API 키뿐이고, 나머지는 시험 도구의 폴더나 동작만 바꿈. 변수마다 없을 때의 동작은 [설정 변수 사전 9절](05_설정_변수_사전.md#9-환경변수)에 있음

## 6. 자주 하는 작업

**이 절의 순서는 2026-10-08에 커밋 `931b217` 코드와 모의 모델로 실제 실행해 확인한 것이며, GPU나 승인이 필요한 명령은 제목과 주석에 표시했다.**

- 예시는 출력 루트를 `OUT=var/demo`(git 제외 폴더)로 둠. 배치·결과 폴더 이름의 날짜(예: `RBATCH-20261008-001`)는 실행한 날짜로 바뀌고, 모의 판정기로 만든 수치는 모델 평가 결과가 아님

### 6.1 입력만 검증하기

**입력 3종만 검사하려면 실행기에 `--validate-only`를 주며, 이때는 모델을 부르지도 폴더를 만들지도 않는다.**

```bash
.venv/bin/python -m kyab_runner.run_single --validate-only [--input <입력 폴더>]   # 기본은 samples/input
```

- 통과하면 `입력 검증: 오류 0건, 경고 0건`을 출력하고 종료 0임. 오류가 있으면 `[error] <표> <item_id>@<item_version> <열>: <이유>` 줄과 `오류가 있어 실행하지 않습니다.`를 출력하고 종료 2임. `turn_index` 같은 정수 열에 숫자가 아닌 값이 있어도 같은 형태로 멈춤
- `--allow-unverified`는 필요 없음. 실행 자격은 검증 뒤 문항을 고를 때 봄. 검증 항목 자체는 [동작 흐름](02_동작_흐름.md)과 [데이터 필드 사전](06_데이터_필드_사전.md)에 있음

### 6.2 모의로 전체 사슬 돌리기

**모의 모델과 모의 판정기로 실행부터 납품까지 확인하는 방법은 두 가지로, 종단 시험을 한 번 돌리거나 단계별 명령을 차례로 돌린다.**

```bash
bash tools/e2e_judge_aggregate.sh            # 한 번에: 결과는 var/e2e_task6/, 마지막 줄이 "e2e 확인 통과"면 성공
OUT=var/demo                                 # 아래는 단계별로 산출물을 볼 때
.venv/bin/python -m kyab_runner.run_single    --allow-unverified --out $OUT
.venv/bin/python -m kyab_runner.run_multiturn --allow-unverified --out $OUT
.venv/bin/python -m kyab_runner.run_multiturn --allow-unverified --out $OUT --mock-plan samples/mock_plan_failures.yaml
.venv/bin/python -m kyab_runner.run_judge $OUT/RBATCH-*
.venv/bin/python tools/apply_judgments.py $OUT/RBATCH-*
.venv/bin/python -m kyab_runner.run_aggregate --allow-mock-judge $OUT/RBATCH-*
.venv/bin/python tools/export_jsonl.py $OUT/RBATCH-* --out var/demo_delivery --results $(ls -d $OUT/RESULTS-* | tail -1) --allow-mock-judge
```

| 단계 | 종료 코드 | 확인한 결과 |
|---|---|---|
| 종단 시험 | 0 | 06 78행, 07 15행 × 2, 분모 보조표 212행. 실모델 자리에 모의 배치 1개를 인자로 준 실행도 통과하고 원본 CSV는 그대로였음 |
| 단일턴 실행 | 0 | 3문항 × 반복 3 = 실행 9건, 모두 `completed` |
| 3턴 실행 | 0 | 실행 9건, 응답 27행, 모두 `completed` |
| 3턴 실패 계획 | 0 | 실행 9건 중 `completed` 5, `partial` 3, `failed` 1. 응답 24행에 차단·오류·시간 초과·빈 응답·절단이 각 1건 |
| 판정 | 0 | 판정 자리 9·36·28개를 모두 판정. 사람 재채점 표본 2·8·6개 표시 |
| 사후 산출 | 0 | 배치마다 `04_runs.csv.bak-<시각>` 백업을 남기고 두 열을 채움 |
| 집계 | 0 | `RESULTS-20261008-001`에 07 15행, 분모 보조표 212행 |
| 납품 변환 | 0 | 파일 10개, 스키마 위반 0, 왕복 차이 0 |

위 명령을 그대로 실행했을 때 단계마다 나온 결과를 적었다. 실패 계획 배치 하나가 차단·오류·시간 초과·빈 응답·절단을 모두 만들어 내서, 정상 경로와 실패 경로가 같은 사슬을 끝까지 통과하는지 한 번에 볼 수 있다. 수치는 모의 모델과 모의 판정기에서 나온 것이라 경로 확인에만 쓰고, 지표 해석에는 쓰지 않는다.

### 6.3 중단된 배치 이어 쓰기

**중단된 배치는 처음과 같은 옵션에 `--batch-id`만 더해 다시 실행하며, 이미 기록된 실행은 건너뛴다.**

```bash
.venv/bin/python -m kyab_runner.run_multiturn --allow-unverified --out $OUT
# Ctrl-C로 중단 → "중단됨. 이어서 실행: --batch-id RBATCH-20261008-001", 종료 130
.venv/bin/python -m kyab_runner.run_multiturn --allow-unverified --out $OUT --batch-id RBATCH-20261008-001
```

| 시점 | 04 행 | 05 행 | 종료 코드 |
|---|---|---|---|
| 중단 직후 | 1 | 6(04에 짝이 없는 3행 포함) | 130 |
| 이어 쓴 뒤 | 9 | 27 | 0 |
| 같은 명령을 한 번 더 | 9(새 기록 0건) | 27 | 0 |

3턴 모의 배치에서 두 번째 실행의 04를 기록하기 직전에 SIGINT를 보내 끊고 이어 써 본 기록이다. 중단 직후에는 04에 오르지 못한 실행의 05 행 3개가 남아 있었지만, 이어 쓸 때 이 행을 걷어 내고 그 실행을 처음부터 다시 해 정상 배치와 같은 04 9행·05 27행이 됐다. 끝난 배치에 같은 명령을 다시 주면 새 기록 0건으로 끝나므로, 이어 쓰기는 여러 번 해도 행이 겹치지 않는다.

- 건너뛰는 기준은 (`item_id`, `item_version`, `model_id`, `rollout_no`)가 04에 이미 있는지임. Ctrl-C가 모델 호출 도중에 들어온 실행도 `stop_reason` `manual_stop`(`partial` 또는 `failed`)으로 04에 기록되므로 다시 하지 않음. 위 표처럼 짝 없는 05 행이 남는 것은 기록을 쓰는 순간에 끊긴 경우이며, 이어 쓸 때 걷어 냄(`kyab_runner/session.py` `discard_orphan_responses`). 끊긴 방식별로 남는 기록은 [동작 흐름 3.9절](02_동작_흐름.md#39-이어-쓰기)에 있음
- `--out`은 처음과 같아야 함(배치 폴더를 `--out` 아래에서 찾음). `protocol_id`, `model_id`, `dataset_version`, 시스템 프롬프트 해시, 입력 파일 sha256, `run_params` 가운데 하나라도 처음과 다르면 `이어 쓸 수 없습니다`와 함께 저장값·현재값을 보여 주고 종료 2임(`kyab_runner/cli.py` `_MANIFEST_LOCKED`). 없는 배치 번호나 형식이 틀린 `--batch-id`는 사전 점검에서 종료 2임

### 6.4 판정 후 집계하기

**판정은 판정, 검증, 사후 산출 순서로 하고, 집계는 기본 규칙과 바꾼 규칙으로 각각 돌려 비교할 수 있다.**

```bash
.venv/bin/python -m kyab_runner.run_judge                 $OUT/RBATCH-*
.venv/bin/python -m kyab_runner.run_judge --validate-only $OUT/RBATCH-*
.venv/bin/python tools/apply_judgments.py --dry-run       $OUT/RBATCH-*
.venv/bin/python tools/apply_judgments.py                 $OUT/RBATCH-*
.venv/bin/python -m kyab_runner.run_aggregate --allow-mock-judge $OUT/RBATCH-*   # 없으면 모의 판정을 종료 2로 거부
sed -e 's/^aggregation_rule_version: 0.2.3/aggregation_rule_version: 0.2.4/' \
    -e 's/^  provider_block_policy: count_as_refusal/  provider_block_policy: exclude/' \
    config/aggregation_rules.yaml > $OUT/rules_exclude.yaml      # 비교용 복사본: 판본을 올리고 차단 정책만 바꿈(현재 판본 0.2.3 기준)
.venv/bin/python -m kyab_runner.run_aggregate --allow-mock-judge --rules $OUT/rules_exclude.yaml $OUT/RBATCH-*
```

| 결과 폴더 | 규칙 판본 | `provider_block_policy` | 모의 판정 사용 |
|---|---|---|---|
| `RESULTS-20261008-001` | 0.2.3 | `count_as_refusal` | true |
| `RESULTS-20261008-002` | 0.2.4 | `exclude` | true |

같은 배치를 두 규칙으로 집계하면 결과 폴더마다 쓴 규칙이 `results_notes.json`에 남는다. 결과 폴더는 고쳐 쓰지 않고 번호가 올라가므로, 두 폴더의 07을 나란히 놓고 정책 하나의 효과만 비교할 수 있다. 코드는 판본을 올리지 않은 복사본도 받아들이므로, 비교용 규칙 파일은 판본을 올려서 만든다.

- 화면 요약은 모델 × 슬라이스마다 주요 지표와 유효 단위·판단 보류 수를 보여 줌. 전체 값은 07과 분모 보조표(`results_denominators.csv`)에 있고, 지표 정의는 [판정과 지표](07_판정과_지표.md)에 있음

### 6.5 납품 폴더 만들기

**납품 폴더는 배치들과 결과 폴더 하나를 묶어 만들고, 마지막 줄의 스키마 위반·왕복 차이가 모두 0이어야 한다.**

```bash
RES=$(ls -d $OUT/RESULTS-* | head -1)            # 함께 넣을 결과 폴더
.venv/bin/python tools/export_jsonl.py $OUT/RBATCH-* --out var/demo_delivery --results $RES --allow-mock-judge
```

- 모델 `mock-echo` 하나로 만든 납품 폴더에는 `manifest.json`과 그 파일 목록에 오른 파일 10개(`items.jsonl`, `responses/`·`judgments/`의 모델별 파일, `results/`의 세 파일, `schema/`의 스키마 세 개, `sources.json`)가 생겼음. 받는 쪽은 납품 매니페스트(`manifest.json`)의 파일 목록과 연결 키를 보고 나머지 파일을 찾아가므로 이 파일부터 읽음. 파일마다 한 줄의 단위, 원천, 필드 구성은 [데이터 필드 사전 5절](06_데이터_필드_사전.md#5-납품-jsonl-구조)에 있음. 원천 CSV가 없는 환경(확인 실행도 이 경우)에서는 `주의: sources.json: ... 원본 파일 없음`이 나오고 `sources.json`의 판본·위치가 빔
- 본평가 납품은 `--allow-mock-judge` 없이 실행하며, 지금은 판정기가 모의뿐이라 종료 2로 거부됨. 러너에 커밋되지 않은 수정이 있으면 납품 매니페스트의 경고로 남으므로 납품 전에 커밋함

### 6.6 공개 모델 서버 띄워 실행하고 끄기 (GPU 필요)

**공개 모델은 vLLM 전용 가상환경을 한 번 만들어 둔 뒤, 서버를 띄우고 실행기에 `--model`을 주고 끝나면 서버를 내려 GPU를 비우는 순서로 쓴다.**

```bash
# GPU 필요: vLLM 전용 가상환경 설치(한 번만). V는 config/runner.yaml 의 vllm_venv 와 같은 경로
V=<작업 폴더>/.venvs/etri-vllm
python3 -m venv --without-pip $V
PIP="python3 -m pip --isolated --no-cache-dir --python $V/bin/python"
$PIP install vllm==0.30.0
$PIP install torch==2.13.0+cu126 torchvision==0.28.0+cu126 torchaudio==2.11.0+cu126 --index-url https://download.pytorch.org/whl/cu126
$PIP install --no-deps torchcodec==0.16.0+cu126 --index-url https://download.pytorch.org/whl/cu126
$PIP install --no-deps --force-reinstall "https://github.com/vllm-project/vllm/releases/download/v0.30.0/vllm-0.30.0%2Bcu129-cp38-abi3-manylinux_2_28_x86_64.whl"
```

- vLLM 가상환경은 러너 가상환경과 따로 두고 고정 판본은 `requirements-vllm.txt`에 있음. 경로에 공백이 없어야 하는데, vLLM이 쓰는 FlashInfer가 첫 실행 때 CUDA 커널을 빌드하다 공백이 든 설치 경로에서 실패하고 심볼릭 링크로도 피할 수 없기 때문임. 작업 서버의 프로젝트 폴더 이름에 공백이 있어 러너 폴더 밖에 둠
- 작업 서버의 NVIDIA 드라이버(570.124.06)는 CUDA 12.8까지 지원하고 PyPI 기본 vLLM 휠은 CUDA 13 빌드라 그대로는 뜨지 않음. 드라이버·시스템 패키지는 건드리지 않고 가상환경 안에서 torch 묶음을 CUDA 12.6 빌드로, vLLM 본체를 CUDA 12 빌드 휠로 바꿈. `--isolated`는 전역 pip 설정의 추가 인덱스가 조회되지 않아 설치가 멈추는 것을 피하려고 씀

```bash
nvidia-smi                                                                        # 다른 작업이 GPU를 쓰는지 먼저 확인
.venv/bin/python tools/vllm_server.py start --model qwen3.8-27b-local --gpu 0     # GPU 필요. 준비될 때까지 기다림
.venv/bin/python tools/vllm_server.py status
.venv/bin/python -m kyab_runner.run_single    --allow-unverified --model qwen3.8-27b-local   # GPU 필요
.venv/bin/python -m kyab_runner.run_multiturn --allow-unverified --model qwen3.8-27b-local   # GPU 필요
.venv/bin/python tools/check_determinism.py samples/output/<run_batch_id>
.venv/bin/python tools/vllm_server.py stop
```

- 이 문서를 쓸 때 가상환경 설치와 GPU 명령은 실행하지 않았음(설치 절차는 작업 서버에서 이 가상환경을 만들 때 쓴 명령임). `status`(기록된 서버 없음, 종료 1), `stop`(종료 0), `start --model mock-echo`(공개 모델 아님, 종료 2)만 실행해 확인함
- `config/models.yaml`에서 `enabled: true`인 공개 모델은 `qwen3.8-27b-local`, `kanana-2-30b-local` 두 개이고, 실측 기동 시간은 각각 약 6.8분, 약 8.6분이었음(H100 80GB 1장, 서버 최대 길이 32,768). 등록된 공개 모델이 모두 포트 8000을 쓰므로 한 번에 하나만 띄우고, 모델을 바꿀 때는 stop 뒤에 start를 실행함
- start는 모델 가중치를 내려받지 않음. HF 캐시에 `config/models.yaml`의 `model_version`과 같은 스냅샷이 없으면 종료 2임. 실행기는 시작할 때 서버가 등록한 이름·스냅샷으로 모델을 올렸는지 확인하고, 서버가 떠 있지 않으면 `어댑터를 만들 수 없습니다`로 종료 2임. `kanana-2-30b-local`은 서버 최대 길이(`max_model_len`)가 바뀌면 같은 입력에도 응답이 달라졌음. 본평가 전 서버 설정을 고정하고, 설정은 `batch_manifest.json`의 `adapter_info`에서 확인함

### 6.7 코드북·분류체계 새 판 반영하기

**코드북 새 판이 오면 판본 상수를 고치고 추출기로 생성 모듈을 다시 만든 뒤, 새 판에 들어간 overlay[^overlay] 항목을 지우고 전체 시험을 돌린다.**

```bash
# 1. tools/extract_codebook.py 의 CODEBOOK_VERSION = "0.2" 를 새 판본으로 고침(손으로)
.venv/bin/python tools/extract_codebook.py --xlsx "<코드북 xlsx 경로>"       # 2. 생성 모듈 다시 만들기
# 3. schema/overlay_v0.3_confirmed.yaml 에서 새 판에 들어간 항목을 지움(전부 들어갔으면 파일 삭제)
.venv/bin/python -m kyab_runner.run_single --validate-only                    # 4. 확인
.venv/bin/python -m unittest discover -s tests
bash tools/e2e_judge_aggregate.sh
.venv/bin/python tools/extract_taxonomy.py --xlsx "<분류체계 xlsx 경로>"     # 분류체계 xlsx가 바뀐 경우
```

- 새 판이 아직 없어 확인 실행에서는 현재 v0.2 코드북과 현재 분류체계 xlsx로 2단계를 실행함. 두 모듈 모두 저장소의 생성 모듈과 바이트 단위로 같았고(분류체계 검산 21항목 통과), 기본 출력 위치로 다시 실행하면 `변경 없음`을 출력함. 3단계를 빼면 overlay의 열 추가 항목이 새 판에 이미 있는 열을 다시 넣으려 해, 코드북을 읽는 진입점(실행기, 판정, 사후 산출, 집계, 납품 변환 등)이 `명세·설정을 읽을 수 없습니다: OverlayError: ... 이미 있는 필드`로 종료 2가 됨. 02 `control_target_risk` 열이 든 코드북으로 현재 overlay를 읽혀 재현함
- overlay 파일이 없으면 생성 모듈만 씀(`kyab_runner/codebook.py` `load_codebook`). 파일을 남길 때 최상위 키는 `base`·`changes`만 받으며 다른 키가 있으면 `OverlayError`로 종료 2임. `base`는 사람이 읽는 출처 표기(현재 생성 모듈 `kyab_runner/spec/codebook_data.py`와 원본 xlsx 이름)라 코드가 읽지 않으므로, 새 판을 반영할 때 손으로 고침
- 생성 모듈은 손으로 고치지 않음. 출력이 의도대로 바뀌었으면 골든 테스트 기준값을 갱신함(3.8). 코드북 열이 바뀌면 `tools/build_samples.py`의 샘플 정의도 맞춰야 하며, 코드북에 없는 열 이름이 있으면 종료 2로 멈춤. 설정·규칙만 바뀌는 경우(재시도 횟수, 판정·집계 결정 등)는 추출기가 아니라 설정 파일을 고치며, 키 목록은 [설정 변수 사전](05_설정_변수_사전.md)에 있음

### 6.8 반복 간 응답 동일 여부 확인하기

**결정성 점검은 실모델 배치에서 의미가 있고, 모의 배치는 구조상 항상 다름으로 나온다.**

- 명령은 `tools/check_determinism.py <배치 폴더> [...]`(3.7)이며, 공개 모델 배치는 6.6의 실행 순서대로 서버를 내리기 전에 확인함. 모의 모델의 정상 응답 본문에는 반복 번호가 들어가므로 모의 배치는 항상 다름(종료 1)으로 나옴. 확인 실행에서도 단일턴 3개 턴, 3턴 9개 턴이 모두 다름이었음. 2026-10-05 공개 모델 두 종의 배치(출력 한도 8,192, 서버 최대 길이 32,768)는 3회 반복 응답이 글자 단위로 같았음

### 6.9 샘플 입력 다시 만들기

**샘플 입력은 원천 CSV가 있을 때만 다시 만들 수 있고, 같은 원본이면 저장소 파일과 바이트 단위로 같아야 한다.**

```bash
.venv/bin/python tools/build_samples.py --data-dir <원천 CSV 폴더> --out <출력 폴더>
cmp <출력 폴더>/01_items.csv samples/input/01_items.csv      # 02·03도 같은 방식
```

- 확인 실행 결과는 01 6행·27열, 02 9행·30열, 03 12행·7열이었고 세 파일 모두 저장소 파일과 같았음. 샘플 바이트가 바뀌면 입력 파일 sha256이 바뀌어, 바뀌기 전 입력으로 만든 배치는 더는 이어 쓸 수 없음

### 6.10 코드를 고친 뒤 확인하기

**코드를 고친 뒤에는 단위 테스트, 종단 시험, 골든 테스트 순서로 돌려 출력이 그대로인지 확인한다.**

```bash
.venv/bin/python -m unittest discover -s tests
bash tools/e2e_judge_aggregate.sh
.venv/bin/python -m unittest discover -s tests -p test_golden.py
```

- 확인 실행에서 전체 테스트는 351개 실행, 실패 0, 건너뜀 3(원본 xlsx·원천 CSV가 없는 환경), 약 40초였고, 작업용 사본에서 `KYAB_UPDATE_GOLDEN=1`로 갱신해도 기준값은 바뀌지 않았음. 출력이 의도대로 바뀐 경우에만 `KYAB_UPDATE_GOLDEN=1`로 기준값을 갱신하고 커밋 메시지에 전후를 적음. 어긋난 내용을 보려면 `KYAB_GOLDEN_DUMP=<폴더>`로 정규화한 출력을 남겨 두 판본을 비교함

### 6.11 상용 모델 실행 (승인 필요)

**상용 모델 3종은 모델 등록부(`config/models.yaml`)에서 꺼져 있어 실행기가 모델을 부르기 전에 거부하며, 켜는 일은 API 키와 유료 집행·외부 전송 조건 승인 뒤에 한다.**

```bash
OPENAI_API_KEY=<키> .venv/bin/python -m kyab_runner.run_single --model gpt-5.6-terra --input <입력 폴더>   # 승인 필요: models.yaml에서 enabled: true로 바꾼 뒤, 키는 환경변수로만 전달
```

- 실행 대상 문항이 있는 입력이면 지금 이 명령은 `모델 'gpt-5.6-terra'은 등록되지 않았거나 enabled: false 입니다`로 종료 2임(샘플 입력에 `--allow-unverified`를 더해 확인함). 실행 대상이 0문항이면 이 점검 전에 종료 1로 끝남. 등록된 상용 모델은 `gpt-5.6-terra`, `claude-sonnet-4.6`, `gemini-3.8-flash`이고 키 변수는 각각 `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`임. 키는 파일에 적지 않으며, 납품 변환은 출력에서 키 패턴을 찾으면 폴더를 지우고 거부함

[^entry]: 진입점: 명령줄에서 직접 실행하는 모듈이나 스크립트.
[^server]: 작업 서버: 러너를 개발하고 공개 모델을 실행한 GPU 서버(H100 80GB 1장).
[^mock]: 모의 모델: 외부 호출 없이 정해진 시나리오대로 응답을 만드는 모델 `mock-echo`(`kyab_runner/adapters/mock.py`).
[^outroot]: 출력 루트: 배치 폴더와 결과 폴더를 담는 상위 폴더. 실행기의 `--out`으로 정함.
[^vllm]: vLLM: 공개 모델을 OpenAI 호환 API로 띄우는 추론 서버.
[^batch]: 배치: 실행 명령 1회의 기록 묶음. 출력 루트 아래 `RBATCH-YYYYMMDD-###` 폴더 하나.
[^manifest]: 배치 매니페스트: 배치의 고정 조건·입력 해시·어댑터 정보를 적은 `batch_manifest.json`. 납품 폴더의 `manifest.json`(납품 매니페스트)과는 다른 파일.
[^mockjudge]: 모의 판정기: 응답 본문의 해시로 점수를 만드는 판정기 `mock-judge`. 실제 채점이 아니어서 본평가에 쓸 수 없음.
[^codebook]: 코드북: 팀 공통 데이터 구조 명세. 7개 CSV(01\~07)의 열 이름·순서·허용값을 정한 xlsx.
[^spec]: 생성 모듈: 코드북·분류체계 xlsx를 기계적으로 옮긴 파이썬 모듈(`kyab_runner/spec/`). 손으로 고치지 않음.
[^protocol]: 프로토콜: 대화 방식과 턴 수의 묶음. `ST1-1.0.0`(단일턴), `MT3-1.0.0`(3턴) 등.
[^preflight]: 사전 점검: 모델을 부르기 전에 인자·설정·어댑터·서버 최대 길이를 확인하는 단계(`kyab_runner/cli.py`의 `preflight`).
[^golden]: 골든 테스트: 같은 입력이면 출력 파일이 바이트 단위로 같은지 기준값(`tests/golden/`)과 대조하는 테스트.
[^overlay]: overlay: 코드북 새 판이 오기 전까지 확정·잠정 변경을 덮어쓰는 yaml(`schema/overlay_v0.3_confirmed.yaml`).
